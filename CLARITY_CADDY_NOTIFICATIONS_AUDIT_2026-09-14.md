# Clarity Caddy notifications — pre-build audit

Date: 2026-09-14  
Scope: current repository implementation only. No production database, Apple Developer, or deployment configuration was changed or inspected.

## Conclusion

Clarity Caddy has the right foundations for one canonical, database-backed notification system, but does not have notification infrastructure today. The recommended V1 is a new server-owned notification domain, with the app reading recipient rows through an authenticated API. Push is a delivery attempt against that same row; Home cards read the same row directly.

The existing course freshness mechanism is the correct trigger and action destination for the first use case. It must be extended with a server-side course relationship record: downloaded-cache state currently exists only in local browser/WebView storage, so a server-side publisher cannot accurately find affected players yet.

## Existing course-update seams

1. `course_visuals.published_version` is the visual map freshness signal exposed by `/api/course-library` as `clarity_map_version`.
2. Frame packages expose `exportVersion`; the client compares it to its cached frame version in `GDCourseVisualEngine.ensureCourseFrames()`.
3. `scripts/gd-app-core.js` receives the existing `onUpdateAvailable` event. This is the right client-side point to record that a signed-in account has a relevant downloaded course, and to reconcile an already-created notification when the player updates.
4. Publishing is server-side via the course visual pipeline. A notification producer should be invoked only once a new published version is authoritative, with an idempotency key of `course_maps_updated:{course_id}:{published_version}`.

## Required V1 model

Use private tables and authenticated Functions rather than browser-accessible notification rows:

- `notifications`: event payload, type, title/body, structured action target, presentation, priority, version/idempotency key, metadata, creation/expiry.
- `notification_recipients`: notification/account pair with read, dismissed, shown, and push-delivery timestamps. A unique notification/account key prevents duplicate Home cards and pushes.
- `device_push_tokens`: account, native installation/device ID, platform, token, enabled state, and last-seen timestamps. Upsert by platform/device ID; replace token rather than treating it as permanent.
- `caddy_course_relationships`: account/course relationship with first/last played, cached/downloaded, and known local map version. This is the server-side targeting proof for `course_maps_updated`.

All four tables need RLS enabled and no broad `anon`/`authenticated` grants. The client-facing Function verifies the Supabase bearer token, resolves `app_accounts.account_id`, and only reads or mutates that account's recipient/device/relationship rows.

## Proposed execution order

1. Add the schema, RLS policies, idempotency constraints, and a server-side notification service that is the only writer of notification and recipient rows.
2. Add authenticated notification APIs for hydration, read/dismiss, device-token upsert, and course-relationship reporting.
3. Add the Home card renderer and one structured action resolver. It should show only the highest-priority active card and fail silently offline.
4. Add reporting from the established course cache/play paths and wire `course_maps_updated` to the published-version event using the relationship table.
5. Add the iOS bridge, permission request at a deliberate Settings/onboarding moment, APNs registration, token upload, and tap-to-action hand-off.
6. Add APNs delivery from the notification service, with invalid-token feedback disabling the device row. Push delivery failure must never roll back the canonical notification row.

## External prerequisites / blockers to production push

No APNs capability or credential configuration is present in the repository. Producing real background/closed-app iOS notifications additionally requires an authorised Apple Developer portal change and secure deployment configuration:

- enable Push Notifications for the Caddy App ID and add the APNs entitlement to the signed target;
- choose APNs token credentials (team ID, key ID, and `.p8` key) and store them only as deployment secrets;
- set the production/sandbox APNs environment and validate against a signed physical device;
- deploy the database migration before the app begins token or recipient API calls.

Those are external, persistent changes and should not be guessed or performed from the source tree. Until they are supplied and authorised, the Home-card and canonical database event system can be built and tested, but claiming working phone push would be inaccurate.

## No duplicate paths to build

- Do not use `NativeRoundBridge` for notifications.
- Do not use `clarity-email.js` as in-app event storage.
- Do not introduce an independent Home-only notification cache.
- Do not add a competing course-version field: retain `published_version` / frame `exportVersion` and the existing shared freshness rule.
- Do not broadcast course updates globally; only recipients backed by `caddy_course_relationships` are eligible.
